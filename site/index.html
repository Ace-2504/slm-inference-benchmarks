When a model writes text, every new token has to look back at every token before it. The KV cache saves the Keys and Values it already worked out so it never redoes that math. I wanted to know what the cache is really worth, so I ran the same greedy decode twice on a 125M model on one NVIDIA L4 — once keeping the cache, once recomputing the whole prefix from scratch at every step. Same prompt, same weights, and the output text comes out identical; the only difference is how much arithmetic gets thrown away.

Here is the part that surprised me. At a batch of 1 the uncached loop computes 60.4× more token positions, and it finishes in basically the same wall-clock time — 0.99×. That looked wrong until I understood why: a single stream barely keeps the GPU busy, so it spends most of its time waiting on memory and the extra math is nearly free. The cache only starts winning once I add enough sequences that the GPU is actually busy doing arithmetic — by batch 16 it is 9.2× faster, and the uncached loop's speed barely moves because it was never limited by arithmetic in the first place.

Speculative decoding is a clever trick. A small draft model guesses k tokens ahead, and the big 7B target checks all of them in a single forward pass, keeping the longest run it agrees with. Because both decode greedily, the final answer is exactly what the 7B would have said on its own — I check that on every run.

And here is the finding that surprised me. My first measurement had it running slower than plain decoding. The honest reason is not the acceptance rate — it is that my 0.5B draft takes 25 ms per step when it should take about 3. It is too small to keep the GPU busy, so it wastes its time launching tiny kernels. I measured c = draft step / target step = 0.428, and once c is that high, no acceptance rate can win. The fix is to run the draft under CUDA graphs — I tried, but it crashed with a device-side error on my torch and transformers versions, so I am reporting the honest c = 0.428 instead of a number I could not reproduce.

The payoff still swings hard by prompt type, and that is the real lesson. On code the draft guesses right 88% of the time and I get 1.53×; on creative prose the draft struggles, the acceptance rate collapses, and it turns into a slowdown. Same mechanism, completely different payoff.

Continuous batching

When you serve many requests at once, the naive thing is static batching: gather a batch, run it, and admit nobody new until every sequence in it has finished. The problem is not speed — it is waiting. Short requests finish early and just sit there holding their slot while one long request runs on. Continuous batching fixes this: the moment a sequence finishes, I evict it and pull a waiting request straight into its slot.

I measured the real decode-step time on the L4 and ran both policies over the same stream of 200 requests with realistic, very uneven output lengths (a few long ones hiding among many short ones — I implemented both sides myself). The chart below is the whole story: static keeps spiking to full and then draining to almost nothing while one straggler finishes, and continuous holds the slots full. At a batch of 32 and 80 requests a second, continuous does 7.5 requests/second against static's 2.5 — about 3× — and its 95th-percentile latency is 14 s against 68 s. Static does not lose because it is slow. It loses because it is idle.

PagedAttention

This one is about memory, and the speed follows from it. The KV cache for a single token is 2 × layers × kv_heads × head_dim × 2 bytes. The trap is kv_heads: Qwen2.5-0.5B uses grouped-query attention, so it has only 2 KV heads, not the 14 attention heads — get that wrong and the whole estimate is off by 7×. For my model that works out to 12 KB per token.

The naive way reserves a full max-length block per sequence up front — 24 MB each for a 2048-token limit. But real answers are short: against my length mix (mean 168 tokens) that wastes 91.8% of the reserved memory. PagedAttention hands out small fixed blocks only as tokens are actually generated. I worked the numbers out, confirmed the naive limit by admitting sequences until the GPU ran out of memory (I predicted 801, it hit the wall at 889), and then confirmed the paged side on the real vLLM engine: it fits 15,220 sequences where naive fits 801 — about 19× more — from the same memory. More sequences resident at once means a bigger effective batch, and that is exactly where the memory saving turns into a speed saving.
